# Architecture

VibeSpec is a local, deterministic transformation pipeline. Its runtime has no service, database, provider SDK, or network boundary.

```text
CLI arguments / UTF-8 idea file
              │
              ▼
       boundary validation
              │
              ▼
       normalized idea model
              │
              ▼
     deterministic rule engine
              │
              ▼
      document renderers
              │
              ▼
 staged bundle + canonical manifest
              │
              ▼
        atomic publication
```

Validation reads the flow in reverse: the manifest defines the exact expected document set and hashes, then each artifact is checked for presence and byte integrity.

## Architecture decision record: language and CLI

**Context:** The project needs a cross-platform console entry point, predictable file handling, strong tests, and low maintenance.

**Options considered:** Python with Typer, Python with standard-library `argparse`, and Node.js with TypeScript.

**Decision:** Python 3.11+ with a `src` package layout and `argparse`. Packaging provides the `vibespec` console script. `pytest` is the only development dependency needed for core testing.

**Trade-offs accepted:** `argparse` requires some manual help/error formatting and offers fewer convenience features than Typer. It avoids a runtime dependency and keeps startup, compatibility, and supply-chain surface small. Python provides less compile-time enforcement than TypeScript, so explicit domain models and boundary validation carry more responsibility.

## Architecture decision record: deterministic rules

**Context:** Free-form ideas are ambiguous, but the MVP must work offline and reproduce output exactly.

**Options considered:** hosted LLM generation, local model inference, and explicit keyword/default rules with Markdown renderers.

**Decision:** Normalize input, apply versioned ordered rules, and render fixed templates. The generated product spec surfaces every default and assumption.

**Trade-offs accepted:** Output is less nuanced and may classify unusual ideas generically. In exchange, behavior is inspectable, free, fast, private, and straightforward to test. An engine interface is the future extension seam; v0.1.0 does not implement providers.

## Modules and responsibilities

- The CLI parses arguments, selects commands, converts domain failures to concise diagnostics, and returns non-zero statuses.
- Input handling reads and normalizes UTF-8 text and rejects empty or malformed ideas.
- Domain models represent the normalized idea, inferred profile, specification sections, tasks, and manifest.
- The rule engine applies ordered, side-effect-free rules. It does not read environment secrets or the network.
- Renderers build the five Markdown documents from the same model so cross-document identifiers remain consistent.
- Bundle writing stages all bytes, calculates hashes, and publishes only after every artifact succeeds. Existing targets are protected unless `--force` is explicit.
- Validation checks required paths, manifest metadata, hashes, and required document structure without executing bundle content.

## Data and determinism contract

Input is decoded as UTF-8. Newlines are normalized before analysis. Output uses UTF-8, LF newlines, stable heading and collection order, and canonical JSON formatting. Generated bytes must not contain current timestamps, random identifiers, absolute host paths, locale-specific formatting, or unordered iteration. Version information may be included because it is fixed for a release.

The manifest, `vibespec.json`, records the format and generator version, project identity and inferred category, a digest of the normalized idea, the required file list, and SHA-256 digests. The manifest itself is excluded from its file-digest map to avoid recursive hashing. The source idea is not copied into the manifest. Validation strictly checks the complete metadata schema and field types. These unkeyed hashes detect changes and corruption only: because anyone can rewrite a document and its manifest hash, they do not authenticate an author or establish trust.

## Filesystem safety

Project names are restricted to a portable safe subset and cannot be absolute paths, traversal segments, drive-qualified paths, or reserved names. Generation writes only beneath the resolved requested destination. A conflict fails before publication. Forced replacement uses a fully prepared staged bundle so a render failure cannot partially update a prior bundle. Validation is read-only.

## Failure model

User errors—empty input, invalid names, mutually exclusive input options, conflicts, missing files, and digest mismatches—produce focused messages without tracebacks. Unexpected internal failures remain distinguishable for debugging, but diagnostics must not expose unrelated environment data or credentials.

## Extension boundary

A future provider may implement the same normalized-model-to-specification interface. It must be explicitly selected and must not change the offline default. Provider output would need schema validation and provenance in the manifest. Network policy, credential handling, nondeterminism, cost, and data retention require separate architecture decisions before such a feature is accepted.

## Testing strategy

Unit tests cover normalization, rule selection, rendering, validation, and path safety. Filesystem tests cover conflicts, force replacement, missing/tampered files, and failure atomicity. Subprocess tests install or invoke the real console surface and assert statuses and diagnostics. Golden or byte comparisons verify repeated generation and cross-platform newline stability. Both committed example ideas are exercised end-to-end.
